01 / מבוא

תקציר מנהלים

Scholarly מרכזת במקום אחד את מחזור החיים המלא של שיעור פרטי: יצירת חשבון, איתור מורה, קביעת שיעור, שינוי מועד, תזכורות, הודעות ודרישת תשלום.

המערכת מיועדת לשני סוגי משתמשים — מורים ותלמידים — ומציגה לכל תפקיד ממשק והרשאות המתאימים לפעולות שלו. המורה מגדיר מחיר ומשך, יוצר שיעורים או משבצות פנויות, מנהל תשלומים ומחבר Gmail. התלמיד מחפש מורים, מזמין משבצת פנויה וצופה בשיעוריו.

02 / הצורך

הבעיה והפתרון

הבעיה

מורים פרטיים מנהלים בדרך כלל יומן, הודעות, ביטולים ותשלומים במספר כלים נפרדים. פיצול זה יוצר כפילויות, קושי לדעת מי קבע מה, שכחה של תזכורות ואיסוף ידני של שיעורים לצורך חיוב.

תיאום מפוזרמועדים עוברים בהודעות ואין מקור נתונים יחיד.
התנגשויותללא בדיקה מרכזית ניתן לקבוע מורה או תלמיד פעמיים.
שינויים מאוחריםקשה לשמור מדיניות ביטול עקבית ולתעד חיוב.
גבייה ידניתאיסוף שיעורים, חישוב סכום ושליחת מסמך דורשים זמן.

הפתרון של Scholarly

המערכת שומרת את המשתמשים, השיעורים והשליחויות במודלים מוגדרים; אוכפת כללי הרשאה והתנגשות בצד השרת; ומציגה בלקוח מידע עדכני באמצעות שכבת נתונים מבוססת TanStack Query.

03 / אפיון

מטרות וקהל יעד

קהל יעד

מורים פרטייםמנהלים תלמידים, שיעורים חוזרים, זמינות, תמחור, תזכורות וגבייה.
תלמידיםמחפשים מורה רשומה, בוחרים משבצת פנויה ומנהלים את השיעורים שנקבעו להם.

מטרות מוצר

  1. מקור אמת יחיד: כל שיעור נשמר עם משתתפים, זמן, נושא, מחיר וסטטוס.
  2. שירות עצמי: תלמיד יכול להזמין משבצת בלי תיאום ידני ממושך.
  3. אוטומציה: יצירת משימות תזכורת ודרישות תשלום על בסיס נתוני השיעורים.
  4. פרטיות והרשאות: כל משתמש רואה ומשנה רק נתונים המותרים לתפקידו.
  5. התאמה מקומית: עברית RTL, אזור הזמן Asia/Jerusalem ולוח עברי לצד הלועזי.
  6. שימושיות: ממשק עקבי, משוב לפעולות, מצבי טעינה והודעות שגיאה.

גבולות המוצר הנוכחי

המערכת אינה מערכת ציונים או מערכת הנהלת חשבונות. מסמך התשלום מוגדר כדרישת תשלום ולא כחשבונית מס או קבלה. WhatsApp ו־SMS מבוססים בשלב זה על משימה ידנית וקישור פתיחה, בעוד Gmail מסוגל לשלוח באמצעות API לאחר חיבור חשבון המורה.

עיקרון תכנון: הקוד מתעדף זרימת שיעור וגבייה אמינה על פני הרחבת המוצר לתחומים שאינם בליבת הבעיה.

05 / דרישות

דרישות איכות ולא־פונקציונליות

אבטחהסיסמאות מגובבות, אסימונים קצרים, refresh token בעוגיית HttpOnly, הרשאות ובדיקת קלט.
עקביותבדיקת התנגשויות ושינויים אטומיים מונעים הזמנה כפולה.
ביצועיםCache בצד הלקוח, אינדקסים במסד וטעינה עצלה של דפים.
תחזוקתיותTypeScript strict, חבילות משותפות, שירותים מופרדים ו־Biome.
זמינות תפעוליתנתיבי health, retries מבוקרים וסטטוס לכל שליחה.
נגישות לשוניתעברית כברירת מחדל, אנגלית, RTL/LTR ועיצוב רספונסיבי.

עקרונות אמינות בקוד

  • תור שליחות מפריד בין יצירת המסמך לבין ניסיון המסירה.
  • יצירת סדרת שיעורים מתגלגלת לאחור אם אחד המופעים נכשל.
  • כשל ביצירת תזכורות מחזיר משבצת למצב הקודם.
  • TanStack Query מרענן cache רק לאחר mutation מוצלח.
  • Axios מבצע ניסיון רענון session יחיד גם כאשר מספר בקשות נכשלות יחד.
  • Zod מחזיר שגיאות קלט עקביות לפני הפעלת לוגיקת התחום.
בדיקה סטטית אינה תחליף לבדיקות אוטומטיות. הפרויקט מגדיר Vitest ו־Supertest, אך בסריקה הנוכחית לא נמצאו קובצי בדיקה פעילים; זהו יעד ברור להמשך.

אחריות רכיבים

  • Web Client: ממשק, ניווט, טפסים, cache וקריאות API.
  • Gateway: נקודת כניסה יחידה וניתוב שקוף לשירות המתאים.

היתרון המרכזי הוא הפרדת אחריות. ניתן לשנות את מנגנון החיוב בלי לערב את ממשק ההזדהות, וכל השירותים משתמשים בחוזים משותפים.
08 / ארכיטקטורה

מבנה ה־Monorepo

scholarly/ ├── apps/ │ └── web-client/ React + Vite ├── services/ │ ├── gateway/ API reverse proxy │ ├── users/ users + authentication │ ├── lessons/ scheduling + reminders │ └── billing/ payments + PDF + delivery ├── packages/ │ ├── shared/ schemas, enums, shared types │ └── utils/ auth, errors, logging, DB helpers ├── scripts/ build utility ├── package.json npm workspaces + root scripts ├── tsconfig.json shared TypeScript configuration └── biome.json formatting and lint rules

למה Monorepo?

חוזים משותפיםתפקידי משתמש, ערוצי שליחה וסכמות Zod מוגדרים פעם אחת.
פקודות אחידותbuild ו־typecheck רצים על כל workspaces מהשורש.
פיתוח מקבילConcurrently מפעיל לקוח וארבעה שירותים יחד.
גבולות ברוריםכל שירות מחזיק package, config, router ו־Dockerfile משלו.

חבילות פנימיות

@scholarly/shared מספקת טיפוסים וסכמות משותפים. @scholarly/utils מספקת אימות JWT, עטיפות controllers, טיפול בשגיאות, לוגים ועזרי Mongoose. כך נמנע שכפול לוגיקה בין השירותים.

11 / חוויית משתמש

ממשק, שפות ולוח שנה

שפה ועיצוב

עברית היא שפת ברירת המחדל, ואנגלית זמינה בבורר השפה. i18next ו־react‑i18next מנהלים תרגומים; שינוי השפה מעדכן גם את lang ואת dir של מסמך ה־HTML. העדפת השפה נשמרת ב־localStorage, בעוד נתוני ההזדהות אינם נשמרים שם.

RTL / LTRיישור וכיוון מתחלפים לפי השפה הפעילה.
עיצוב רספונסיביGrid, Flex ו־Tailwind מתאימים את הכרטיסים למסכים שונים.
משוב מיידיToast, spinner, disabled states ו־Error Boundary.
רכיבים עקבייםButton, Card, Input, Label ו־Form מקומיים מעל Radix UI.

לוח שנה כפול

@hebcal/core ממיר כל יום לייצוג עברי, כולל גימטריה וחגים. רכיב בחירת המועד משלב יום לועזי, תאריך עברי ושעה. כללי סדרות וזמני מערכת משתמשים ב־Luxon ובאזור הזמן Asia/Jerusalem.

13 / Users Service

משתמשים והזדהות

מודל משתמש

אוסף המשתמשים משתמש ב־Mongoose discriminator עבור teacher ו־student. לכל משתמש שם, אימייל, טלפון, הסכמות וסיסמה מגובבת. למורה נוספים חשבון בנק והעדפות שיעור.

מחזור session

→

→

+
Refresh · 7d
  • Access token נשמר בזיכרון היישום בלבד ומצורף כ־Bearer token.
  • Refresh token אקראי נשמר בדפדפן בעוגיית HttpOnly ו־SameSite=Lax.
  • במסד נשמר SHA‑256 של refresh token, לא האסימון הגולמי.
  • פעולת refresh מוחקת את הרשומה הקודמת ויוצרת session חדש.
  • Axios interceptor מרענן session אחרי 401 ומנסה שוב את הבקשה המקורית.

פרטיות

רשימת המורים/תלמידים מחזירה נתוני directory מצומצמים. גישה לפרופיל ולעדכון משתמש דורשת התאמה בין מזהה הנתיב לבין ה־sub שב־JWT. פרטי בנק אינם מוחזרים ב־session או במסך הפרופיל.

הגנה כפולה: ProtectedRoute משפר את חוויית המשתמש, אך כל API רגיש מאמת JWT והרשאה בצד השרת — המקום היחיד שניתן לסמוך עליו.

יצירה ותמחור

המורה יכול ליצור משבצת ללא תלמיד או שיעור משויך. משך ומחיר נקבעים לפי סדר עדיפויות: ערך שנשלח בפעולה, override של הנושא, ואז ברירת המחדל של המורה. משך שיעור מוגבל ל־15–240 דקות.

כללי תקינות

  • רק מורה רשאי ליצור שיעור, ורק עם teacherId שלו.
  • מועד חדש חייב להיות בעתיד.

  • הקביעה נעשית בתנאי שהרשומה עדיין זמינה וללא תלמיד.
  • לאחר קביעה נוצרות תזכורות ל־30 שעות ול־30 דקות לפני המועד.

סדרות חוזרות

Luxon מחשבת מופעים באזור הזמן של המורה לפי מרווח שבועות, מספר מופעים או תאריך סיום. נדרשים לפחות שני מופעים, וברירת המחדל העליונה היא 104. אם מופע אחד נכשל, המופעים והתזכורות שכבר נוצרו נמחקים.

19 / Security

אבטחת מידע

סיסמאותbcrypt עם מספר rounds ניתן להגדרה ומגבלת 72 בתים.
JWTissuer, audience, tokenType, תוקף 15 דקות וסוד מינימלי של 32 תווים.
Refresh sessionsאסימון אקראי של 48 בתים, hash במסד, תוקף 7 ימים וסיבוב בכל refresh.
CookiesHttpOnly, SameSite=Lax, Secure בסביבת production ונתיב מוגבל.
Authorizationבדיקות role, self ו־participant בכל תחום.
Input validationZod בצד הלקוח ובכניסה לנתיבי Express.
Signed linksHMAC‑SHA‑256 והשוואה קבועת זמן למסמכים וקישורי פתיחה.
OAuth secretsAES‑256‑GCM, IV ו־authentication tag עבור refresh token.

הקשחת HTTP ופרטיות

Helmet מוסיף כותרות אבטחה, CORS מגביל origins ומאפשר credentials רק למקורות מוגדרים. תגובות משתמש מצומצמות לפי הקשר, סיסמה אינה נבחרת כברירת מחדל במודל, ופרטי בנק אינם נשלחים ב־session.

ניהול סודות: JWT secret, מפתח הצפנה ופרטי OAuth מגיעים ממשתני סביבה ואינם אמורים להישמר בקוד המקור.

26 / Quality

איכות, טיפול בתקלות ולוגים

בצד הלקוח

  • Error Boundary מונע מקריסת רכיב להשאיר דף ריק.
  • TanStack Query מספק מצבי pending, error ו־success וניסיון חוזר מוגבל.
  • Toast מציג משוב לפעולה, וכפתורים ננעלים במהלך mutation.
  • Axios ממיר שגיאת שרת ל־Error אחיד ומטפל ב־401 דרך refresh.

בצד השרת

  • שגיאות תחום כוללות status code וקוד פנימי.
  • ZodError מוחזר כ־400 עם הסבר ברור.
  • Express Winston מתעד בקשות לפי status level.
  • נתיבי health מאפשרים בדיקת חיות בסיסית.

דרישות מקדימות

שלבים

  1. התקנת כל workspaces באמצעות npm install בשורש.
  2. יצירת קובצי .env לפי .env.example בכל שירות.
  3. הגדרת JWT_SECRET זהה ובאורך 32 תווים לפחות בשירותים הרלוונטיים.
  4. הגדרת MONGO_URI, מקורות CORS וכתובות השירותים ב־Gateway.
  5. בחיובים: הגדרת מפתח הצפנה, סוד מסמכים, כתובות Web/API ו־Chromium.
  6. הפעלת סביבת הפיתוח באמצעות npm run dev.
